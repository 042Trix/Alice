# Methodology M — Decide graph readiness

> A graph (loop or master-ticket flow) is "product-ready" only when it has cleared a documented promotion bar. The `live` vs `live-pending-test` status field in the loop registry is the durable surface; the 9-item promotion criteria below are the rubric the registry's status must satisfy. Without this methodology, the registry's status is heuristic — what looks `live` to one operator is `live-pending-test` to another, and the gap between "shipped" and "trusted" is invisible.

## Part 1: Why this methodology

Alice is methodology that other operators apply to their own setups. If Alice does not define what makes a loop "product-ready," then a friend reading Alice has no way to know whether to trust a `live` label they see in a loop registry, whether to wait for `live-pending-test` to clear, or what work remains between the two. The operator's current environment already has the gap: as of 2026-08-14, of 10 registered loops in `~/.hermes/loops/hermes.yaml`, only 1 (`alice-publish`) carries `status: live`; the other 9 carry `status: live-pending-test`. The status field exists; the rubric that justifies moving from one to the other does not.

This methodology fills the gap with four things:

1. **Semantics** — what `live` and `live-pending-test` actually mean (Part 2)
2. **Promotion criteria** — the 9 items, split into 6 verifier gates + 3 promotion gates (Part 3)
3. **Product-ready inventory** — what a well-defined graph carries (Part 4)
4. **Verification discipline** — how to actually test readiness (Part 5)

The methodology is **tool-agnostic**: any work-graph system with a status field can apply it. The canonical implementation lives in the Hermes loop registry (`~/.hermes/loops/hermes.yaml` + `~/.hermes/loops/intents/<loop-id>-intent.md`) and the per-loop regression suites (`~/.hermes/tests/test_<loop_id>_*.py`). The friend reading Alice later can apply the same 9 items to their own loop registry.

## Part 2: `live` vs `live-pending-test` semantics

### `live`

A graph is at `live` when ALL of the following hold:

- **Contract documented.** The methodology doc + intent doc + yaml entry + tests all agree on what the graph does. Reading any one of them gives the same answer to "what does this graph do and when does it succeed?"
- **Regression suite green.** All test cases pass on the current version. The test surface is in `~/.hermes/tests/test_<loop_id>_*.py` (or equivalent).
- **Production usage proven.** The graph has been used end-to-end at least once with operator-confirmed success (a Discord DM, a kanban comment, a vault audit-line, or a child-ticket handoff).
- **Paired-wiki integrity.** Per op-guard-5 (`2-ATOMIC/rules/op-guard-5-wiki-update-2026-07-21.md`): the methodology doc + intent doc + yaml entry + tests ship in the same change set.
- **Compliance-gate satisfied.** Per op-guard-17 (`2-ATOMIC/rules/op-guard-17-methodology-canonical-instance-conforms-2026-08-08.md`): a verifier child confirms the instance conforms to the Alice doc. For a loop, this is a verifier ticket that runs the regression suite and confirms the dispatcher binding matches the contract.

### `live-pending-test`

A graph is at `live-pending-test` when ALL of the following hold:

- **Works in practice** but the formal verification is incomplete — the loop has been used but the regression suite is partial or the audit hasn't run.
- **Used by the operator** at least once (even informally) — `live-pending-test` is not "draft"; it means "actually works, just not yet proven to the standard of `live`."
- **Has at least one test case green** — a smoke test, a unit test, or a verified end-to-end run. The full regression suite is not required at `live-pending-test`; the loop is honest about what it's verified for.

A graph at `draft` (no production usage) is NOT a graph; it's a spec. Specs live on the `alice-framework` board as methodology docs; loops live on the operator's instance with status `live-pending-test` or `live`. The two states (spec vs loop) are distinct from the two loop states (`live-pending-test` vs `live`).

### Promotion is a two-act play: correctness first, then transition

The `live` label only earns after both acts complete:

- **Act 1 — Verifier gates (correctness):** the 6 verifier-gate items (1, 2, 4, 6, 8, 9) are all true. The verifier profile PASSES the compliance-verifier child (op-guard-17) with `--result "compliance: pass"`.
- **Act 2 — Promotion gates (transition):** the operator dispositions PROMOTE via HITL (item 7, per op-guard-32); the system flips the yaml `status:` field to `live` (item 3); the compliance-verifier PASS is recorded (item 5). The audit-line appends (op-guard-11).

Operator review (item 7) is a 4-stage HITL (per op-guard-32) — scope/intent → intent-achievement → compliance → disposition. The operator's `clarify-<ISO-timestamp>` decision_ref captures each stage's disposition; collapsing the 4 stages into a single yes/no hides intent-achievement failures that the rubric would otherwise catch (a loop can pass compliance yet not currently achieve the intent).

A loop cannot reach `live` by satisfying only correctness — the operator's HITL is required. A loop cannot reach `live` by satisfying only disposition — `status: live` is a substance claim, not a disposition claim (per op-guard-30). Both acts must complete.

## Part 3: Promotion criteria (9-item table — verifier gates vs promotion gates)

> **v0.1.2 refinement** (per `t_a61e5611`, operator 2026-08-18): the 9-item rubric is split into two groups — 6 **verifier gates** (what the verifier profile evaluates for correctness) and 3 **promotion gates** (what indicates the loop has been promoted). Items 3, 5, and 7 conflated three different concerns in v0.1.1: yaml status (a post-flip surface), operator HITL (the operator's decision), and the verifier-PASS itself (a chicken/egg). The refined rubric separates them so each can be evaluated correctly.

A loop is ready to promote from `live-pending-test` → `live` when ALL of the following are true: (1) all 6 verifier gates are correct (verifier PASS recorded per item 5); (2) the operator dispositions all 4 HITL sub-gates per op-guard-32 (item 7); (3) the system flips the yaml `status:` field to `live` (item 3).

### Group A — Verifier gates (6 items: 1, 2, 4, 6, 8, 9)

The verifier profile walks these 6 items and PASSES the compliance-verifier child ticket if all 6 are correct. These items are **what the work product is** — the verifier confirms the work was done correctly, not whether anyone agreed to it.

| # | Item | Required? | Source of truth |
|---|------|-----------|-----------------|
| 1 | Methodology doc exists + cross-references the loop | ✅ | `~/Documents/alice-framework/methodology/M-decide-<loop-name>.md` (or generic methodology like `04a-decide-work-graph.md`) with a `links:` field that names the loop id. **AND the methodology doc accurately describes the work-graph's current behavior** — the verifier reads the doc + walks the actual graph (master ticket + children + dispatcher routing + verifier chain); a methodology doc that exists + cross-references the loop but is STALE (its per-node descriptions no longer match the actual child tickets' worker profiles / scopes / outcomes) FAILS this gate. The paired-wiki existence check (op-guard-5) confirms the doc is on disk + cross-references the loop; this sub-check confirms the doc is CORRECT — the substance matches the form. A doc that exists + cross-references the loop but describes a different graph is a documentation convention, not a `live`-readiness gate. |
| 2 | Intent doc exists + `version:` field is bumped | ✅ | `~/.hermes/loops/intents/<loop-id>-intent.md` — frontmatter `version:` field tracks semver per `loop-updater` discipline |
|| 4 | Regression suite exists + green | ✅ | `~/.hermes/tests/test_<loop_id>_*.py` (or `test_<loop_id>_<aspect>_*.py`); all test cases exit 0; a `pytest -q` run captures the green. **AND the regression suite asserts observable behavior, not implementation tautologies** — at least one test per regression suite asserts behavior visible from the operator's chat (a master ticket filed, a Discord DM delivered, a kanban comment posted, an audit-line appended). The companion verification discipline is Part 5 check 1 (a) (b) (c) (d) (e); (a/b/c) is the v0.2.0 amend-1 contract (HIGHEST priority per 2026-08-18 council synthesis, 5/5 seats agreed); (d/e) is the v0.2.4 amendment (`t_d187a655`) that ships the 3-class verifier classifier — ✅ Behavior / ⚠️ Tautology / ❌ Trivial — and the PASS/FAIL rule (tautology_count==0 AND trivial_count==0 AND ≥1 Behavior) that the verifier enforces. A regression suite that passes only by tautological assertions (e.g., `assert loop_status == "live"` after the flip without an end-to-end behavior check) is a documentation convention, not a `live`-readiness gate — the canonical production-disaster pattern; the v0.2.4 classifier is the verifier procedure that proves the contract is enforced. |
| 6 | Paired-wiki integrity per op-guard-5 | ✅ | The same change set ships methodology doc + intent bump + yaml `status:` flip + regression suite updates; `kanban_complete` carries the file-list as evidence. **AND the change set is atomic** — all four artifacts (methodology doc + intent doc + yaml `status:` flip + regression suite updates) appear in the same commit (or explicitly chained commits within the same PR / change set, with no intermediate state where one ships without the other). Two commits in close succession can look like "paired changes" in git history but are not atomic; a race condition (e.g., the loop's yaml entry ships first while the methodology doc ships second) could land partial changes that pass the paired check but fail the atomicity check. The op-guard-5 paired-wiki integrity is the existence check; atomicity is the correctness check. |
|| 8 | Loop has been used end-to-end at least once **with a successful run** | ✅ | `kanban show <loop_run_card>` shows a `loop-run — <loop-id> v<X.Y.Z> — result=success` audit-line at `~/Documents/HermesVault/log.md`, **AND** the run completed successfully — the card's terminal status is `done` per `kanban show <loop_run_card>` (not `blocked`, not `running-then-blocked`, not `running-then-cancelled`); no retry storm (the card's event log shows `< 3` retries); no escalation (the audit-line log shows no `operator-action-dm` triggered by this run, per op-guard-13). A run that completed via `kanban_block` does NOT satisfy item 8 (the operator disposition is acceptable evidence for op-guard-30's evidence/exemptions but NOT for item 8's "successful run" requirement). The `result=success` audit-line label alone is insufficient when paired with a `blocked` terminal status — the substance claim (run outcome) governs, not the audit-line label. A loop with only failed runs is not `live`-ready; the failure modes must be resolved before the run counts toward item 8 (the loop must be re-fired with the failure-mode fix). |
| 9 | **Node-type discipline** — every node in the graph uses the appropriate type per `methodology/04a-decide-work-graph.md` Part 4 (Human / Scripts/Code / Agents — LLM-driven Agents for interpretation, Scripts/Code for determinism, Human for operator-owned decisions) + the rationale for each type choice is documented | ✅ | The graph's design doc names each node + its type + the rationale; the verifier profile reads the design doc + walks each node to confirm the type matches the work |

### Group B — Promotion gates (3 items: 3, 5, 7)

These items are NOT checked by the verifier. They are the **transition triggers** — what indicates the loop has actually been promoted. The verifier cannot evaluate them because each one is a different kind of external truth:

- Item 3 = a yaml field that does not exist before the flip.
- Item 7 = an operator decision the verifier cannot observe.
- Item 5 = the verifier-PASS itself (the verifier cannot record PASS without first passing).

| # | Item | Type | What it checks | When it fires |
|---|------|------|----------------|---------------|
| 3 | **YAML status** | **Promotion gate — post-flip** | `status: live` after verifier PASS + operator HITL | AFTER items 1, 2, 4, 6, 8, 9 pass + verifier PASS + operator disposition PROMOTE |
| 5 | **Compliance-verifier** | **Promotion gate — verifier PASS recorded** | Did the verifier record PASS for the 6 verifier gates? | Recorded by the verifier in the same turn as the PASS transition |
| 7 | **Operator HITL** | **Promotion gate — pre-flip** | Did the operator disposition via HITL per op-guard-32? The operator's HITL is 4-stage: HITL #1 — scope/intent (CONFIRM / REVISE / ABANDON); HITL #2 — intent-achievement (ACHIEVES / PARTIALLY-ACHIEVES / DOES-NOT-ACHIEVE); HITL #3 — compliance (CONFIRM / DISPUTE / EXEMPTION); HITL #4 — disposition (PROMOTE / DEFER / ARCHIVE). Item 7 is satisfied only when all 4 sub-gates fire (or skip-conditions per op-guard-32). | BEFORE the yaml flip fires |

#### 4-stage HITL structure (item 7)

**Item 7 is satisfied only when the operator dispositions all 4 HITL sub-gates** (per op-guard-32, `2-ATOMIC/rules/op-guard-32-four-stage-graph-hitl-2026-08-17.md`). The 4 sub-gates fire in order, each via `clarify` (per op-guard-24), and each captures a `clarify-<ISO-timestamp>` decision_ref per op-guard-10 v2 §1.2:

| Sub-gate | Question summary | Choices | Fires when |
|----------|------------------|---------|------------|
| **HITL #1 — Scope/intent** | Confirm the loop's purpose + scope | `CONFIRM` / `REVISE` / `ABANDON` | Before any audit work; on REVISE → intent doc + methodology doc update + rewrites + HITL #2 re-checks |
| **HITL #2 — Intent-achievement** | Confirm the graph currently achieves the intent (per recent run history) | `ACHIEVES` / `PARTIALLY-ACHIEVES` / `DOES-NOT-ACHIEVE` | After HITL #1 passes; on PARTIALLY/DOES-NOT → chat-side files rewrite tickets before HITL #3 |
| **HITL #3 — Compliance** | Confirm the 9-item rubric score + per-item evidence per op-guard-30 | `CONFIRM` / `DISPUTE` / `EXEMPTION` | After HITL #2 = `ACHIEVES`; on DISPUTE → re-run audit + fire HITL #3 again; on EXEMPTION → document per op-guard-30 4-field schema |
| **HITL #4 — Disposition** | Confirm the operator's final PROMOTE / DEFER / ARCHIVE choice | `PROMOTE` / `DEFER` / `ARCHIVE` | After HITL #3 passes; PROMOTE flips the yaml per item 3 |

**Why 4 stages, not 1.** Collapsing the operator's review into a single yes/no PROMOTE hides intent-achievement failures (HITL #2) and compliance disputes (HITL #3). A loop can pass compliance (items 1, 2, 4, 6, 8, 9 all ✅) yet still NOT currently achieve the intent (e.g., a cron that fires hourly when the intent is "fire daily at 9am"). The 4-stage structure catches both classes of failure at the operator's disposition step, before the yaml flip fires.

**24h re-prompt rule (per op-guard-29).** Each sub-gate is independently skipped if the operator already dispositioned it within the last 24h. The per-loop disposition cache lives at `~/.hermes/cron/output/<slug>/loop_dispositions.json` (per op-guard-29); the chat-side reads the cache before invoking `clarify` to honor the 24h rule. This prevents churn: a loop dispositioned PROMOTE yesterday doesn't re-prompt the operator today unless something changed. The 24h clock is per-gate, not per-loop — a HITL #1 `CONFIRM` from 23h ago still skips HITL #1, but a HITL #3 EXEMPTION from 25h ago does NOT skip HITL #3.

**Skip conditions (per op-guard-32, summary).** Each sub-gate may skip when its individual skip condition fires:

- HITL #1 — Loop has never been used (no runs) AND operator already dispositioned the loop's scope in chat within 24h.
- HITL #2 — Loop is at `status: live` (grandfathered) AND no scope/intent changes within 24h.
- HITL #3 — Loop has 9/9 audit score AND no exemptions needed.
- HITL #4 — Operator already dispositioned the loop within the last 24h.

**All other conditions: the gate MUST fire.** Partial audits (firing only some sub-gates without skip conditions) are forbidden; item 7 is FAIL until all 4 sub-gates pass (or skip with documented skip-condition).

### The promotion procedure (refined)

The actual promotion procedure is the canonical contract. Each step has a precondition and an artifact:

1. **Verifier checks the 6 verifier gates** (items 1, 2, 4, 6, 8, 9). PASS or FAIL.
   - **PASS condition:** all 6 verifier gates are correct.
   - **FAIL condition:** any verifier gate is incorrect → file a fix-up ticket; re-run after the fix.
   - **Artifact:** the compliance-verifier child ticket (op-guard-17) transitions to `done` with `--result "compliance: pass"`.
2. **Operator HITL fires** (item 7, per op-guard-32 4-stage gates: scope/intent → intent-achievement → compliance → disposition).
   - HITL #1 — scope/intent (CONFIRM / REVISE / ABANDON).
   - HITL #2 — intent-achievement (ACHIEVES / PARTIALLY-ACHIEVES / DOES-NOT-ACHIEVE).
   - HITL #3 — compliance (CONFIRM / DISPUTE / EXEMPTION).
   - HITL #4 — disposition (PROMOTE / DEFER / ARCHIVE).
   - **Artifact:** `clarify-<ISO-timestamp>` decision_ref per op-guard-10 v2 §1.2 + per op-guard-32.
3. **YAML flip fires** (items 3 + 5) — only after verifier PASS + operator disposition PROMOTE.
   - Flip `loops[].status = "live"` in `~/.hermes/loops/hermes.yaml` (item 3).
   - Record verifier PASS in the audit-line (item 5).
   - Bump intent doc `version:` field per semver.
   - Append audit-line to `~/Documents/HermesVault/log.md` per op-guard-11.

### Why this split matters

The v0.1.1 rubric conflated three distinct concerns:

- **Verifier gates** (what the verifier checks for correctness)
- **HITL gates** (what the operator dispositions)
- **Promotion gates** (what indicates the loop has been promoted)

Conflation caused:

- **Circular dependencies** (item 3 = "yaml is `live`" was a verifier gate, but `live` is the destination of promotion)
- **Chicken/egg** (item 5 = "verifier PASS" was a verifier gate, but the verifier cannot record PASS without first passing)
- **Operator-can't-see-9/9** (item 7 = "operator review" was a verifier gate, so the operator could never see a 9/9 score until they had already dispositioned)

The v0.1.2 split resolves each:

- **Item 3 is post-flip** — the verifier does NOT check `status: live`; the system flips it after PASS.
- **Item 5 is the verifier-PASS itself** — the verifier records PASS, period; the rubric doesn't ask whether it PASSed, the PASS itself is item 5.
- **Item 7 is operator HITL** — it's the operator's disposition, surfaced via `clarify`, captured as `decision_ref`. The verifier doesn't check this; the operator decides.

### The audit score after v0.1.2

The score `loop_live_audit.py` reports is: **6/6 verifier + 1 HITL + 1 flip**. This is the canonical presentation (per council synthesis 2026-08-18 amendment #6, `t_5581cb91`); the previous "6 + 1 + 1 = 8 gate-events" / "9/9" framings were ambiguous because they conflated three distinct things:

- **6/6 verifier** — what the verifier checks (items 1, 2, 4, 6, 8, 9). The verifier PASSES only when all 6 are correct.
- **1 HITL** — what the operator dispositions (item 7). The 4-stage HITL (per op-guard-32) collapses to 1 disposition event for the score; the 4 stages are the sub-gates that compose that event.
- **1 flip** — what the system does after both pass (items 3 + 5). The yaml `status:` field flips to `live` and the audit-line records the verifier PASS.

A loop can have 6/6 verifier gates + 1 operator HITL dispositioned PROMOTE and still be at `live-pending-test` until the 1 flip fires. The flip is the transition; the score is the state. The canonical phrasing is "**6/6 verifier + 1 HITL + 1 flip**" — do NOT use "8/8" or "9/9" (both are misleading: 8/8 obscures the verifier-vs-HITL distinction; 9/9 conflates the 3 promotion gates with the 6 verifier gates).

### Anti-pattern: claiming `live` without verifier PASS or operator HITL

The `alice-publish` loop was promoted to `live` on 2026-08-11 with items 1–4 + 6–8 satisfied (verifier gates under the v0.1.1 framing). Items 5 (compliance-verifier child) and 9 (node-type discipline) are newer than the original promotion — op-guard-17 shipped 2026-08-08 (three days before the promotion); item 9 shipped 2026-08-15 (v0.1.1 of this methodology, four days after the promotion). For `alice-publish`, item 5 is backfilled by the 2026-08-15 retrospective verifier ticket; item 9 holds in practice — the publish flow uses Scripts/Code for git operations + verifier gates + minimal Human operator approval per Part 7.5, with no Agent nodes doing deterministic work. Future promotions MUST carry the verifier PASS + operator HITL + yaml flip chain per the v0.1.2 procedure; pre-2026-08-18 promotions of `live` loops are grandfathered under the v0.1.1 rubric (items 1–6 + 7–8 + 9). Re-promotion (re-running the audit on a `live` loop) follows the v0.1.2 procedure.

## Part 4: Minimum items for a product-ready graph

A "well-defined product-ready graph" carries the following inventory. The inventory is the **artifact list** that a new graph (or a freshly-promoted loop) must have on the day it's labeled `live`. Missing items block `live` until they're added or explicitly deferred with an aspirational-flag.

### A. Documentation triad (paired-wiki per op-guard-5)

- **Methodology doc** — the contract. Names what the graph does, when to use it, what the inputs/outputs are, what the failure modes are. Lives on `alice-framework` board at `~/Documents/alice-framework/methodology/`.
- **Intent doc** — the implementation. Names the `worker_prompt`, the dispatcher registration, the runtime cadence, the verifier hook. Lives at `~/.hermes/loops/intents/<loop-id>-intent.md`.
- **Yaml entry** — the dispatcher binding. Names the loop id, the `register_with_profile` + `run_with_profile`, the `target_board`, the `status`, the `context_as_budget`. Lives at `~/.hermes/loops/hermes.yaml`.

The triad is **atomic for promotion**: a change to any one of the three without the other two is a paired-wiki violation per op-guard-5. The change set MUST be a single commit (or atomic PR) carrying all three artifacts (plus the regression suite from §B); intermediate states are NOT acceptable. Atomicity is the correctness check that op-guard-5's paired-wiki integrity check enforces — the verifier on instance-side confirms via `git log --format=%H --grep='<change set name>' -10` that no intermediate commit existed where the yaml entry shipped without the methodology doc (or vice versa). Two commits in close succession can look like "paired changes" in git history but are not atomic; see Part 3 item 6 for the canonical atomicity clause.

The triad is also **internally consistent**: each artifact must agree with the others on what the graph does. Methodology describes intent; intent describes yaml; yaml describes tests; tests assert behavior the methodology describes. A methodology doc that names 5 nodes but the intent doc's worker_prompt only references 4 is a consistency violation; a yaml entry that registers a `register_with_profile` the intent doc doesn't list is a consistency violation; a regression suite that tests 3 nodes but the methodology doc describes 5 is a consistency violation. The verifier walks all four documents (methodology + intent + yaml + tests) and confirms node counts, names, worker profiles, and outcomes agree across them — see Part 5 check 3 (d) for the per-child-ticket consistency walk that backs item 1's "methodology doc accurately describes the work-graph's current behavior" sub-check. Paired-wiki integrity (item 6) is the existence check (the four artifacts ship together); this consistency check is the correctness check (the four artifacts describe the same graph).

### B. Test coverage (compliance-gate per op-guard-17)

- **Unit tests** — individual functions validated. E.g., `test_post_graph_retro_spec_drift.py` validates the spec-drift detector; `test_loops_preflight_profile_home.py` validates the preflight.
- **Integration tests** — end-to-end dispatcher + worker spawn + `kanban_complete` cycle. E.g., `test_x_article_review_loop_v080.py` validates the x-article-review loop end-to-end.
- **Regression suite** — golden cases from verified failure patterns. Each post-mortem (in `2-ATOMIC/post-mortems/`) that motivated a fix should map to a test case in the regression suite.
- **Behavior-asserting tests + 3-class verifier classifier (v0.2.4).** Tests must assert observable behavior the operator can verify end-to-end (e.g., master ticket files on the right board, child ticket has the right body, audit-line appends), not implementation tautologies (e.g., `assert loop_status == "live"` after the flip). The verifier classifies each test in the regression suite as one of three classes:
  - ✅ **Behavior test** — asserts observable output the operator can verify without reading the loop's source (a function's return value, a file's content, an API response, a database row, an audit-line written, a `kanban_create` payload, a Discord DM delivered, a YAML field actually flipped at runtime).
  - ⚠️ **Tautology test** — asserts the implementation matches itself (no external observable): `assert dispatcher.is_pinned() == True` after the dispatcher just flipped its own flag; `assert yaml_status == "live"` after the code that flipped it ran; `assert loop_id == LOOP_ID` in a test that hard-codes `LOOP_ID = "x-article-review"`; `return foo() == foo()`. The test is green via self-reference, not via the spec.
  - ❌ **Trivial test** — asserts nothing meaningful: `assert True`, `assert 1 == 1`, an `except: pass` block, a `return None` stub, an empty function body.

  At least one ✅ Behavior test is required per regression suite. If the regression suite contains **any** ⚠️ Tautology test or ❌ Trivial test, item 4 FAILS regardless of how green the suite is — the verifier transitions the compliance-verifier child to `done --result "compliance: fail — item-4-tautology-or-trivial-test — <loop_id> v<X.Y.Z>: <N> tautologies + <M> trivial in <test_file>"`. A regression suite that is 100% green via tautological or trivial assertions is a documentation convention, not a `live`-readiness gate — the canonical production-disaster pattern. Sub-check: see Part 5 check 1 (a) (b) (c) (d) (e) for the verification discipline that enforces this; see Part 3 item 4 row for the source-of-truth reference; canonical classifier implementation: `~/.hermes/tests/test_graph_readiness_rubric_v0_2_0_item4.py` (4-case regression ships green in 0.01s — passes when all behaviors, fails when any tautology or trivial is present). The companion instance-side tool (`~/.hermes/tools/verifier_test_classifier.py`) ships via a separate coder/verifier ticket per the spec-first flow op-guard-16 + the op-guard-17 compliance-verifier chain.
- **Verifiers** — child tickets that confirm the instance matches the contract. Per op-guard-17, the verifier child is the META's done-gate child. The verifier walks the 6 verifier gates (Part 3 Group A); it does NOT walk items 3, 5, 7 (those are promotion gates — see Part 5).

### C. Operational contract

- **Run history preservation** — `run_history.preserve_done: true` + `run_history.never_archive_loop_runs: true` in the yaml. The loop's run history is durable; archiving it loses the audit trail.
- **Audit-line discipline** — every loop transition appends an audit-line to `~/Documents/HermesVault/log.md` via `vault_log.append_audit_line` per op-guard-11. The audit-line schema is in `run_history.audit_line_schema` on the yaml entry.
- **Operator-facing surface** — Discord DM, kanban comment, or vault copy. The loop's outcome is reachable from chat. The `deliver` field on the cron registration (or the equivalent for on-demand loops) names the surface.
- **Error handling** — `transient` failures retry with backoff; `hard-failure` failures transition to `blocked` for operator review. The protocol-violation retry (per op-guard-15) is the canonical pattern for worker-side failures.
- **Error handling discipline** — a `live` loop must demonstrate successful completion of at least one end-to-end run. A loop with only failed runs is not `live`-ready — the loop's failure modes (retry storms, escalations, `kanban_block` outcomes) must be resolved before the run counts toward item 8 (Part 3). The substance-claim governs: a `result=success` audit-line label paired with a `blocked` terminal status does NOT satisfy item 8; the loop must be re-fired with the failure-mode fix and complete cleanly via `kanban_complete` before the verifier PASS can fire.

### D. Discipline gates

- **Op-guard-19** (pre-verify artifact state before claiming done) — the verifier profile runs `verify_artifact_state.py` before `kanban_complete`.
- **Op-guard-21** (chat-side orchestrator-only, no direct edits) — the loop's environment mutations go through the worker protocol; the chat-side files tickets, doesn't edit files.
- **Op-guard-22** (canonical handoff write discipline) — when the loop ends a session, both the dated handoff and `session-handoff.md` get written atomically.
- **Op-guard-30** (promotion requires evidence or exemptions) — the flip is a substance claim; the system only flips `status: live` after verifier PASS + operator disposition + per-item evidence on file (or documented exemptions per the 4-field schema).
- **Op-guard-32** (4-stage graph HITL) — the operator dispositions each loop via 4 gates: scope/intent → intent-achievement → compliance → disposition. The verifier does not disposition HITL.
- **Node-type discipline** (Part 3 item 9 + Part 4 of `04a-decide-work-graph.md`) — every node uses its proper type (Human / Scripts/Code / Agents). A loop that has an Agent (LLM-driven) node doing work a script could do deterministically is not `live`-ready even if items 1–6 + 8 + 9 are all green; the item-9 gate violation is a release-blocker that supersedes items 1–6 + 8. The x-article-review rebuild (v0.9.7 → v0.9.36, 13 amendments) is the canonical example — each amendment made a previously-Agent-interpreted step a Scripts/Code path; the same discipline must hold forward.

The discipline gates are NOT loop-specific; they're cross-cutting. A loop that violates any of them in its regression suite is not `live`-ready even if the 9-item rubric is satisfied; the gate violation is a release-blocker.

## Part 5: Verification discipline

To verify a graph is `live`-ready (i.e., to run the verifier-side of the promotion procedure), the verifier profile walks the 6 verifier gates from Part 3 Group A and produces a PASS or FAIL. Items 3, 5, 7 are NOT verifier-checked; the verifier records PASS as item 5 and the system flips item 3 after the operator dispositions item 7. Each check maps to a subset of the 6 verifier gates:

1. **Run the regression suite.** `pytest -q ~/.hermes/tests/test_<loop_id>_*.py`. (Verifier gate 4.) The check verifies:
   - **(a)** All test cases exit 0 (the green surface).
   - **(b)** At least one test per regression suite asserts behavior visible from the operator's chat — a master ticket filed on the right board, a child ticket with the right body, a Discord DM delivered, a kanban comment posted, an audit-line appended to `~/Documents/HermesVault/log.md`. The behavior must be observable by the operator without reading the loop's source code; it tests the spec, not the implementation.
   - **(c)** No test asserts only the implementation surface (no `assert yaml_status == "live"` after the flip without an end-to-end behavior check; no `assert dispatcher.is_pinned() == True` without a follow-on assertion that the dispatcher's child actually ran). A regression suite that is 100% green via implementation tautologies is a documentation convention, not a `live`-readiness gate — the canonical production-disaster pattern (a `live` label backed by tests that prove only the implementation surface, not the spec). This sub-check is v0.2.0 amend-1; the council synthesis 2026-08-18 rated it HIGHEST priority (5/5 seats agreed).
   - **(d) (v0.2.4) Classify every test via the 3-class verifier classifier.** The verifier invokes `python3 ~/.hermes/tools/verifier_test_classifier.py <test_file>` for each test file in the regression suite (or imports the classifier when the verifier runs inline). Each test gets one of three labels — ✅ Behavior, ⚠️ Tautology, ❌ Trivial — based on the canonical definitions in Part 4 §B. The classifier inspects the test's AST for self-reference patterns (assertions on values the test itself just set / values reached only via the implementation under test / `assert True` / `assert 1 == 1` / `except: pass` / empty function bodies). The classifier produces a per-test classification report and a suite-level roll-up (`{tautology_count, trivial_count, behavior_count}`).
   - **(e) (v0.2.4) Item 4 PASS / FAIL rule.** Item 4 PASSES only when (i) every test exits 0 (sub-check a), AND (ii) at least one test is ✅ Behavior (sub-clause b), AND (iii) `tautology_count == 0` (sub-clause d), AND (iv) `trivial_count == 0` (sub-clause d). If ANY tautology or trivial is detected, the verifier transitions the compliance-verifier child to `done --result "compliance: fail — item-4-tautology-or-trivial-test — <loop_id> v<X.Y.Z>: tautologies=<N> trivial=<M> in <test_file>"` and item 4 fails; the loop cannot promote to `live` until the tautologies / trivial tests are removed or rewritten. The canonical 4-case regression suite: `~/.hermes/tests/test_graph_readiness_rubric_v0_2_0_item4.py` (lives next to the v0.2.5 amend's `test_graph_readiness_rubric_v0_2_0.py` to avoid filename collision; the v0.2.4 amend owns this file, the v0.2.5 amend owns the shared filename). All 4 cases green in 0.01s; covers (1) all Behavior → PASS, (2) one Tautology → FAIL, (3) one Trivial → FAIL, (4) mixed (2 Behavior + 1 Tautology + 1 Trivial) → FAIL. The (d) + (e) sub-clauses were added in the v0.2.4 amendment (this ticket `t_d187a655`) to make the v0.2.0 amend-1 contract enforceable: the (a)/(b)/(c) prose specifies the contract; (d)/(e) is the verifier procedure that proves it.
2. **Trigger the loop via dispatcher.** File a master ticket on the loop's `target_board` (or fire the cron if `trigger.kind: cron`). Verify a child ticket lands on the right board with the right body. (Verifier gate 8.) The check also verifies:
   - **(a)** The child ticket lands on the loop's `target_board` per the intent doc (not a drifted board).
   - **(b)** The child ticket's body matches the `worker_prompt` schema from the intent doc (registered_run + worker_prompt + audit_line_schema fields all present).
   - **(c)** The run's terminal outcome is `done` per `kanban show <loop_run_card>`. If the run is `blocked` or transitioned through `blocked` en route to completion, item 8 is NOT satisfied — the loop must be re-fired with the failure-mode fix. The check inspects the card's event log for retry storms (≥3 retries in a 5-minute window signals a retry storm) and the audit-line log at `~/Documents/HermesVault/log.md` for `operator-action-dm` triggers tied to this run (any `operator-action-dm` invocation is an escalation; item 8 requires neither retry storm nor escalation). A run that completed via `kanban_block` does NOT satisfy item 8. On item-8 failure the verifier returns `compliance: fail — item-8-failed-run — <loop_id> v<X.Y.Z>: terminal=<status> after <N> retries, <M> escalation-dm events` and the loop must be re-fired with the failure-mode fix before re-audit.
3. **Verify the master ticket's children are filed correctly.** Parent edges, bodies, gates, dispatch profiles all match the contract in the intent doc. (Verifier gates 1, 2.) The check also verifies:
   - **(a)** The intent doc's per-child contract matches the actual child ticket's `assignee` + scope + outcome (worker profile is one of `jarvis` / `coder` / `planner` / `verifier` / `doc-writer` / `business-analyst` / `council` / `marketing` / `msaa-scout` / `web-research`).
   - **(b)** The parent edge relationship in the kanban DB matches the intent doc's described dependency graph (no orphan children, no missing edges, no extra edges).
   - **(c)** The dispatcher routing on each child matches the intent doc's described `target_board` (no cross-board leakage, no missed dispatch).
   - **(d)** **For each child ticket, the methodology doc's per-node description matches the actual child ticket's worker profile + scope + outcome.** The verifier opens the methodology doc, walks each per-node description (e.g., "Agent node for web-research", "Human node for operator HITL", "Scripts/Code node for compliance check"), and confirms the corresponding child ticket's assignee + body + outcome reflect that description. A mismatch between the methodology doc's per-node description and the actual child ticket's substance is a FAIL — the doc is stale or the implementation drifted; either way, item 1's "methodology doc accurately describes the work-graph's current behavior" sub-check fails. The sub-check backs item 1 by giving the verifier a concrete procedure: walk the doc, walk the graph, compare node-by-node. |
4. **Verify the worker spawn + run + complete cycle.** A worker profile claims the ticket, runs the worker_prompt, and transitions to `done` via `kanban_complete` with structured handoff. (Verifier gate 4 + verifier gate 6.) The check also verifies:
   - **(a)** The worker ran the canonical `worker_prompt` from the intent doc (not a drifted prompt).
   - **(b)** The `kanban_complete` call carries structured metadata (`changed_files`, `tests_run`, decisions).
   - **(c)** If the work changed any of the four paired-wiki artifacts (methodology / intent / yaml / tests), the `kanban_complete` `created_cards` list includes a verifier child per op-guard-17.
   - **(d)** The atomicity of the change set: `git log --format=%H --grep='<change set name>' -10` shows that no intermediate commit existed where the yaml entry shipped without the methodology doc (or vice versa). `git show <commit> --stat` lists all four artifacts in the same commit. The atomicity check is the correctness check that backs op-guard-5's paired-wiki existence check (Part 3 item 6); without it, two close-succession commits could pass the existence check but fail the correctness check.
5. **Verify the audit-line discipline.** Every transition (`claim`, `complete`, `block`) appends a line to `~/Documents/HermesVault/log.md` per the schema in `run_history.audit_line_schema`. (Operational contract §C.)
6. **Verify the operator-facing surface.** The Discord DM, kanban comment, or vault copy carries the loop's outcome to the operator's chat. (Operational contract §C.)
7. **Verify failure paths.** Inject a transient failure (e.g., a missing file the loop expects) and confirm the loop retries. Inject a hard failure (e.g., a malformed yaml entry) and confirm the loop transitions to `blocked`. (Operational contract §C.)
8. **Verify node-type discipline.** Walk the graph's design doc (the methodology doc + the intent doc). For each node, confirm:
   - The node's type matches the work it does (Agents only when interpretation is needed, Scripts/Code when determinism is possible, Human only for operator decisions — per Part 4 of `methodology/04a-decide-work-graph.md`).
   - The rationale for the type choice is documented (one line per node, why this type and not another).
   - Under failure injection, the node behaves as expected for its type: Scripts/Code nodes fail loudly with a deterministic error message; Agents produce bounded output that the next validator enforces; Human nodes gate a decision the agent cannot make on the operator's behalf. (Verifier gate 9 + Discipline gate §D.)

If a node fails check 8, the verifier does NOT pass the compliance-verifier child. The child transitions to `done` with `--result "compliance: fail — node-type-discipline violation on <node-id>, expected type=<X>, actual type=<Y>, rationale missing or post-hoc"`. The META ticket cannot promote the loop; the design doc must be amended, the rationale rewritten, and check 8 re-run.

If all 8 checks pass (which is equivalent to all 6 verifier gates being correct), the verifier transitions the compliance-verifier child to `done` with `--result "compliance: pass"` — this is promotion-gate item 5 firing. The META ticket can then fire HITL (promotion-gate item 7) and the system flips the yaml `status:` field (promotion-gate item 3) per the Part 3 procedure.

**The verifier never evaluates items 3, 7.** Item 3 is a post-flip surface (the yaml state after the transition); the verifier does not read its own reward. Item 7 is the operator's disposition (op-guard-32); the verifier is not the operator. The verifier evaluates the 6 verifier gates (1, 2, 4, 6, 8, 9) and records PASS as item 5; the operator + system complete the promotion via items 3 + 7.

## Part 6: How to apply this methodology

When a new loop is added to the operator's environment:

1. **File the spec-first-flow methodology doc** on `alice-framework` (this methodology provides the rubric; the loop's specific doc is filed per `M-decide-spec-first-flow.md` Part 2).
2. **File the intent doc + yaml entry** on the operator's instance (per the loop-updater loop's `worker_prompt` and the canonical `register_with_profile` / `run_with_profile` discipline). Initial status: `live-pending-test`.
3. **File the regression suite** at `~/.hermes/tests/test_<loop_id>_*.py` with at least one test case green. (Verifier gates 4, 8.)
4. **Trigger the loop at least once** to produce a run history entry. The run can be operator-driven or cron-driven. (Verifier gate 8.)
5. **File the bulk-promotion META** when the 6 verifier gates are all green. The META's compliance-verifier child (per op-guard-17) runs the 8 checks from Part 5.
6. **On compliance-verifier pass, fire the operator HITL gates** per op-guard-32 (scope/intent → intent-achievement → compliance → disposition). Operator dispositions PROMOTE / DEFER / ARCHIVE.
7. **On disposition PROMOTE + verifier PASS, flip the yaml `status:` field** to `live` and bump the intent doc `version:` field per semver. Append an audit-line. The loop is now `live`.

A loop that has been at `live-pending-test` for 30+ days without promotion is a signal that either (a) the loop is not worth the work to promote (consider archiving per `04a-decide-work-graph.md` Part 7 — work graph node retirement) or (b) the loop's contract has drifted (re-run verifier gates 1, 6).
